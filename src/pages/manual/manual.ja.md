# BGPShark ユーザーマニュアル

BGPShark は、パケットキャプチャを解析して BGP セッションの状態を可視化するツールです。セッションが上がらない、フラップする、経路が届かない、意図しない上流へ抜けるといった障害調査に利用できます。

すべての処理はブラウザ内で完結します。キャプチャファイルが外部にアップロードされることはなく、オフライン環境でもそのまま動作します。ヘッダ右上の **EN / 日本語** ボタンで UI 全体の表示言語を切り替えられます。

## キャプチャの読み込み {#loading-a-capture}

ウィンドウ内の任意の場所へファイルをドラッグ＆ドロップするか、開始画面のファイル選択から読み込みます。`.pcap`、`.pcapng`、`.cap` 形式（最大 50 MB）に対応しており、ファイル形式は自動で判別されます。

サイズの大きなキャプチャでは読み込みに数秒かかり、進行状況がプログレスバーに表示されます。所要時間の大部分は最終段階の **DuckDB へ読み込み中** で、大規模な経路テーブル転送では数百万行のデータをインポートします。

手元にキャプチャがない場合は、**sample.pcapng で試す** でサンプルデータを試せます。右上の **⋯** メニューの **作成** から、検証用のキャプチャを作ることもできます。

読み込んだキャプチャはブラウザ内のストレージ（IndexedDB）に保存されるため、ページをリロードしても保持されます。別のファイルを読み込む場合は、左上のファイル名をクリックしてください。

### 解析結果に違和感があるとき {#if-the-capture-looks-wrong}

ヘッダー下に黄色い警告バナーが表示された場合、ファイルの一部（途中で切れたフレームや破損したブロックなど）を正常にパースできなかったことを示します。バナーをクリックすると詳細を確認でき、問題のない残りのパケットはそのまま解析されます。

解析結果を読む際は、以下の 3 点に注意してください。

- **片方向のみのキャプチャは検出事項として報告されますが、原因の切り分けが必要です。** 片方向しか観測できないセッションは critical の検出事項として報告されますが、ミラーポートや `tcpdump` フィルタの設定ミスなのか、片方向リンクや ACL による実際の通信障害なのかは区別できません。見分け方は [キャプチャが不完全な可能性を確認する](#the-capture-may-be-lying-to-you) を参照してください。
- **TCP レベルのフレームは既定では非表示です。** パケット一覧は初期状態では BGP メッセージのみを表示します。TCP の RST（`[R]`）や FIN（`[F]`）を確認するには **すべてのパケット** に切り替えてください。**すべてのパケット** でもフィルタは有効です。BGP を含まないフレームには `src_ip`・`dst_ip`・`src_port`・`dst_port`・`frame` の条件だけが評価されるため、`src_ip = 10.0.13.1` ならそのピアの BGP と併せて TCP ハンドシェイクや切断も表示され、`type = UPDATE` のような BGP 専用の条件では該当する BGP フレームだけが残ります。
- **セッション途中から取得したキャプチャには OPEN が含まれません。** 4 バイト AS の利用有無や ADD-PATH の Path Identifier の有無は OPEN でネゴシエートされ、UPDATE 単体には明示されません。OPEN が欠けている場合、BGPShark はメッセージ構造からエンコーディングを推定し、警告バナーにその旨を表示します。可能であればセッション確立前から再取得してください。

## 各画面の使い方 {#the-screens}

キャプチャを読み込むと、1 つのワークスペースが開きます。左の列にはキャプチャ内の **セッション** と **検出事項** を表示し、右側に各画面をタブで並べます。上部には **時間軸** の帯があります。迷った場合は、まず検出事項を確認するか、[症状から調べる](#investigating-by-symptom) から該当するケースを選んでください。

| タブ | 主な用途 |
|------|----------|
| **メッセージ** | 送受信されたメッセージの詳細と生バイトを確認する |
| **セッション** | ピア同士が OPEN で合意した内容と、セッションの確立・切断の経緯を確認する |
| **経路** | 特定プレフィックスの広告・取り消し履歴や属性を確認する |
| **SQL** | 複数プレフィックスやセッションをまたぐ自由な集計・検索を行う |

**作成**、**ヘルプ**、ソースコードへのリンクは、右上の **⋯** メニューにまとめています。

### ワークスペース {#the-workspace}

**セッション** には、BGP をやり取りした（または TCP ポート 179 で接続を試みた）アドレスの組をすべて表示します。AS 番号、メッセージ数、最も重い検出事項もあわせて表示します。セッションを選ぶと、**すべてのタブ** がそのセッションに絞られます。対象はパケット一覧、経路、時間軸、検出事項です。選択中のセッションはタブ行の右端に表示されます。そこにある **×** か **すべてのセッション** をクリックすると、キャプチャ全体の表示に戻ります。

**検出事項** は、キャプチャから見つかった問題です。パケット単位ではなく、問題の種類ごとに 1 行にまとめます。たとえば 3 セッションを持つルータの Hard Reset は、3 行ではなく *NOTIFICATION: Cease / Hard Reset ×3* の 1 行になります。最も重い種類が先頭にあり、最初から展開されています。行をクリックすると個々の発生箇所が一覧になり、発生箇所をクリックすると **メッセージ** で該当パケットが開きます。このときフィルタも自動で設定されます。検出事項を開いても選択中のセッションは変わらないので、同じ問題の発生箇所を順にたどれます。

検出の対象は、NOTIFICATION、セッションフラップ、Withdraw バースト、経路フラップ、同一ピアからの AS_PATH 変化、EVPN の MAC ムーブ、Graceful Restart、NOTIFICATION なしの TCP 切断、片方向セッション、TCP 接続後に BGP 応答がないケースです。*Cease / Connection Collision Resolution* は **参考** として最後に表示します。両端が同時に接続した際に一方の接続を閉じる BGP の通常動作（RFC 4271 §6.8）であり、障害ではないためです。また、*異なる*ピアからの AS_PATH の違い（iBGP ピアの空のパスと eBGP ピアの `65001` など）は正常なので通知しません。比較は **経路** で行ってください。

> 「問題は検出されませんでした」はセッション層に異常がないことを意味します。経路リークや意図しないベストパス選択など、ポリシー上の問題はセッションが健全なため検出されません。

**時間軸** は、キャプチャ全体を通したメッセージ数を表示します（セッションを選んでいれば、そのセッションの分だけ）。NOTIFICATION は赤い線で示します。帯の上をドラッグすると、**メッセージ** と **経路** がその期間に絞られます。帯をクリックするか **全期間に戻す** を押すと元に戻ります。検出事項、OPEN の比較、SQL は常にキャプチャ全体が対象です。

### メッセージ {#messages}

パケット一覧、階層化された詳細ビュー、折りたたみ式の 16 進ダンプを表示します。行をクリックすると、ケイパビリティやパス属性までデコードされた内容と生バイトを確認できます。

**情報** 列には各メッセージの要約が表示されます（OPEN なら `AS65001 Hold=90`、UPDATE なら広告プレフィックスと取り消し線付きの取り消しプレフィックス（多い場合は `+N`）、NOTIFICATION ならエラー名）。NLRI も Withdraw も含まない空の UPDATE は **End-of-RIB** と表示されます。

フィルタ行の右端にある **列設定** で、タイムスタンプやポート番号の列を切り替えられます。一覧の下の行には表示中のパケット数を表示し、そこにある **pcap 出力** で表示中のパケットだけを新しい `.pcap` として保存できます（チケット添付用に関連パケットだけを切り出す用途に便利です）。KEEPALIVE だけの行は薄く表示し、何かを変えた行が目立つようにしています。

各 UPDATE は 1 枚のカードにまとまり、広告・取り消しプレフィックス（MP_REACH/MP_UNREACH_NLRI 内のものを含む）とパス属性をそれぞれ 1 回だけ表示します。**生データ** は折りたたまれており、開いた状態は `↑`/`↓` でのパケット移動後も維持されます。KEEPALIVE では、送信元の直前メッセージからの経過時間と、それがネゴシエート済み Hold Time の何 % にあたるかを表示します。**メッセージ** から別タブへ移動してタブから戻ると、フィルタ・**すべてのパケット** モード・選択中のフレームが復元されます。

### セッション {#sessions}

セッションを選んでいないときは、全セッションの一覧表を表示します。表には AS 番号と iBGP／eBGP の別、キャプチャ終了時点の状態、メッセージ数、最も重い検出事項が並びます。行をクリックする（または左の列でセッションを選ぶ）と、そのセッションを開きます。

セッションを選ぶと、上から次の内容を表示します。

- 状態、双方が合意した Hold Time、NOTIFICATION とメッセージの件数、各端が広告・取り消しした経路の数
- **OPEN の比較**: 各端の最新の OPEN を並べて比較します。
- **出来事**: OPEN と NOTIFICATION を、直前からの経過時間付きで一覧表示します（**すべて** で全メッセージを表示します）。クリックすると **メッセージ** で開きます。

ケイパビリティはアドレスファミリ（AFI/SAFI）単位で比較され、不一致の項目が先頭に表示されます。Hold Time の違いは仕様上問題ない（小さい値が採用される）ため情報表示にとどめ、BGP Identifier の重複はエラーとして強調します。

### 経路 {#routes}

キャプチャ内の全プレフィックスについて、広告回数、取り消し（Withdraw）回数、最終観測時刻、**フラップ** 回数を一覧表示します。**フラップ** 列でソートすると不安定な経路をすぐに見つけられ、プレフィックスをクリックすると全履歴と AS_PATH を確認できます（広い画面では先頭のプレフィックスが自動で開きます）。検索は入力に合わせて即時反映されます。履歴の行をクリックすると、そのプレフィックスで絞り込んだ **メッセージ** が該当 UPDATE を選択した状態で開きます。

検索ボックスでは 3 つの照合モードを切り替えられます。

- **完全一致** — 入力したプレフィックスと完全一致するもののみ表示します。
- **サブネット** — 入力した CIDR に含まれるより細かい経路を検索します（例：`10.0.0.0/8` で `10.0.12.0/24` がヒット）。
- **スーパーネット** — 入力した IP アドレスや CIDR を包含する集約経路を検索します（例：`10.0.12.7` で `10.0.0.0/8` がヒット）。

### SQL {#sql}

キャプチャを DuckDB のテーブルとして SQL で直接クエリできます。標準画面では対応できない横断的な比較や集計に利用してください。サイドバーの **スキーマ** には全テーブル・全カラムが型付きで表示され、名前をクリックするとエディタのカーソル位置に挿入されます。代表的なクエリ例は **クエリテンプレート** に用意されています。エディタは右下の角をドラッグして高さを変えられます。

結果の `frame_index` の値をクリックすると **メッセージ** でそのフレームが、`prefix` の値をクリックすると **経路** でその経路履歴が開きます（同じ行に `prefix_length` があれば完全一致の経路を開きます）。

クエリを書く際のポイントは以下の 3 点です。

- `nlri.prefix` にはプレフィックス長が含まれないため、`prefix || '/' || prefix_length` で結合して表示してください。
- `nlri`、`as_path`、`path_attributes` はいずれも `message_id` で結合するため、3 つをそのまま JOIN すると行が直積で膨らみます。相関サブクエリを使用してください。
- テーブルは検索用に平坦化したデータです。全フィールドの詳細を確認したい場合は `frame_index` から **メッセージ** 画面を参照してください。

同じプレフィックスに対する複数経路の属性を比較するクエリ例：

```sql
select n.prefix || '/' || n.prefix_length as route, p.src_ip,
       (select string_agg(a.asn, ' ' order by a.as_index)
          from as_path a where a.message_id = m.id) as as_path,
       (select max(med_value)  from path_attributes where message_id = m.id) as med,
       (select max(local_pref) from path_attributes where message_id = m.id) as local_pref
from nlri n
  join messages m on m.id = n.message_id
  join packets p using (frame_index)
order by route
```

### 作成 {#build}

ラボ環境を用意せずに、セッション構成を記述するだけで有効な `.pcap` ファイルを生成できます。事前にキャプチャを読み込む必要はありません。

8 種類のプリセット（正常なセッション確立、Hold Timer 満了、AS 番号の不一致、TCP 接続拒否、IPv6 トランスポート、経路フラップ、4 バイト AS 番号、TCP セグメント分割された UPDATE）から選び、ピア情報・経路・メッセージ手順を編集して、プレビュー確認やダウンロードを行えます。

UPDATE のエンコーディング（4 バイト AS 幅や ADD-PATH Path Identifier）は OPEN のケイパビリティ設定から自動で決定され、TCP セグメント分割は MTU 設定に従います（MTU を下げるとセグメントをまたぐ BGP メッセージを生成できます）。チェックサムも正しく計算されるため、出力した `.pcap` は Wireshark など他のツールでもそのまま開けます。

## 症状から調べる {#investigating-by-symptom}

実際の障害症状から、確認すべき画面と判断のポイントを逆引きできます。

### 最初に確認すること {#start-here}

どの症状であっても、まず次の 3 ステップから確認してください。

1. 左列の **検出事項** を確認します。最も重い種類が先頭にあり、最初から展開されています。
2. キャプチャに双方向のパケットが含まれているか確認します（[キャプチャが不完全な可能性を確認する](#the-capture-may-be-lying-to-you)）。
3. 先頭の検出事項の項目をクリックし、フィルタ済みの状態で起点パケットを確認します。

![フラップしているセッションのワークスペース。左にセッション一覧と検出事項、上に NOTIFICATION を赤線で示す時間軸、右にパケット一覧を表示](manual/workspace.png)

「問題は検出されませんでした。すべてのセッションは正常です。」と表示されていても、それはセッション層が健全であることを示すだけです。経路リークやベストパス選択の異常は別途確認する必要があります。

### 「セッションが確立しない」 {#the-session-will-not-come-up}

ネイバーが Idle または Connect のままで BGP メッセージがやり取りされない場合、TCP ポート 179 への SYN に対する応答を確認します。

**検出事項** を確認します。BGP メッセージが一切含まれないキャプチャでは、TCP 層から検出事項が生成されます。

![critical の検出事項「TCP connections to port 179 are being refused — 3 SYNs answered by RST」](manual/s1-tcp-refused.png)

- **SYN に RST が返る** — ACL やファイアウォールによる拒否、TCP-MD5 / TCP-AO の不一致、あるいは対向ルータで BGP が待ち受けていない状態です。
- **SYN に応答がない** — BGP より下位のルーティング障害やパケット破棄（フィルタリング）が起きています。
- **SYN-ACK のあと BGP が来ない** — **検出事項** に *「TCP 接続後に 10.0.0.2 から BGP 応答がありません」* と表示されます。TCP ハンドシェイクが成立しているため、ポートは開いており、ACL による SYN 破棄や TCP-MD5 不一致は除外できます。対向のネイバー設定漏れ、TCP ミドルボックス、PMTU ブラックホール、コントロールプレーンポリシングなどを確認してください。

リトライ回数や間隔を確認するには、**メッセージ** を **すべてのパケット** モードに切り替えます（**BGP のみ** では何も表示されません）。

### 「Established だが特定のアドレスファミリの経路が来ない」 {#it-is-established-but-a-whole-address-family-never-arrives}

セッションは確立し IPv4 経路は正常なのに、IPv6・EVPN・VPNv4 などの経路がまったく届かない場合はケイパビリティの不一致を確認します。

左列でセッションを選び、**セッション** タブを開くと **OPEN の比較** が表示されます。

![Capability Diff。セッション基本項目は一致し、IPv6/Unicast Multiprotocol Extensions を含む 4 つのケイパビリティが片側のみ広告されている](manual/s2-capability-diff.png)

**状態** 列を確認してください。

- **⚠ *x* のみ** — 片側しか広告していないケイパビリティ／アドレスファミリです。双方で有効にしない限り、そのアドレスファミリの経路は交換されません。
- **異なる AS（eBGP では正常）**（My AS）や Hold Time の差異は正常です。
- **BGP Identifier の重複** はエラーとして表示されます。

### 「数分おきにセッションがフラップする」 {#it-flaps-every-few-minutes}

**検出事項** では、繰り返された切断が回数付きの NOTIFICATION 1 行にまとまり、セッションフラップの警告と並んで表示されます。

![検出事項「NOTIFICATION: Hold Timer Expired / Unspecific ×3」と「Session flapping detected — 6 OPEN messages (~3 establishments)」](manual/s3-holdtimer-alerts.png)

`Hold Timer Expired` は対向からのメッセージが一定時間届かなかったことを意味します。**メッセージ** で該当の NOTIFICATION をクリックし、**切断までの無応答時間** を確認してください。

![NOTIFICATION の詳細。ネゴシエートされた Hold Time 90 秒に対し、10.0.0.1 からの最終 KEEPALIVE から 90.4 秒経過している](manual/s3-holdtimer-gap.png)

- **無応答時間 ≧ ネゴシエートされた Hold Time**（例：90 秒に対して 90.4 秒）：セッション自体は稼働していたものの、片方向で KEEPALIVE が届かなくなっています。BGP 設定ではなくルータ間の通信経路を調査してください。
- **無応答時間が Hold Time より大幅に短い**：タイマーの早期発火として警告表示されます。キャプチャのパケット取りこぼしか、記録された OPEN と異なる Hold Time が有効になっていた可能性があります。

無応答時間は単純な直前パケット（自ルータの KEEPALIVE の場合がある）ではなく、**対向ピアの最終メッセージ** から計測され、その切断直前の OPEN でネゴシエートされた小さい方の Hold Time と比較されます。OPEN がキャプチャに含まれない場合は、無応答時間のみが表示されます。

### 「理由が記録されないままセッションが切断された」 {#it-dropped-and-nothing-says-why}

NOTIFICATION が出力されないままセッションが切断・再確立している場合、TCP 層での切断が起きています。

**検出事項** を確認します。NOTIFICATION なしの切断は、切断の種類ごとに critical の検出事項として表示されます。

- *「…が NOTIFICATION なしで RST 切断されました」*（TCP RST — ファイアウォールやソケットリセットなど能動的な切断）
- *「…が NOTIFICATION なしで FIN 切断されました」*（TCP FIN — セッションアイドルタイムアウトなど正常クローズによる切断）

どちらかの検出事項をクリックすると、**メッセージ** が自動で **すべてのパケット** モードに切り替わり、該当フレームが選択されます。

![検出事項に「was reset with no NOTIFICATION」と「was closed with no NOTIFICATION」の 2 件の critical、その下に「Session flapping detected」を表示](manual/s11-teardown-alerts.png)

これらの検出事項は *「セッションフラップを検知しました」* と併用して確認します（フラップ警告は再確立の回数、切断の検出事項はどのように切れたかを示します）。なお、一度も確立しなかったセッションは *「TCP 接続後に … から BGP 応答がありません」* 側で扱われるため、ここには表示されません。

手動で確認する場合は **メッセージ** を **すべてのパケット** に切り替えます（**BGP のみ** 表示でフレーム番号が飛んでいる箇所が手がかりになります）。

![All Packets モードでフレーム 11 を選択。10.0.0.2 からの [AR] フレームと、詳細ペインの「TCP Flags: ACK, RST」を表示](manual/s11-tcp-reset.png)

`[AR]` は ACK+RST、`[F]` は FIN を表します。TCP フラグ専用のフィルタフィールドはないため、**すべてのパケット** モードで直接確認してください。

### 「経路を広告した直後にセッションが落ちる」 {#the-session-drops-the-moment-routes-are-advertised}

セッション確立後、最初の UPDATE を送った直後に切断される場合は、**メッセージ** で該当の NOTIFICATION をクリックします。

![NOTIFICATION の詳細。エラーコード 3 UPDATE Message Error、サブコード 2 Unrecognized Well-known Attribute、トラブルシューティングヒント、Well-known・Transitive とデコードされた UNKNOWN(199) および生バイトを表示](manual/s6-notification.png)

エラーコード **3**（`UPDATE Message Error`）とサブコード（`Unrecognized Well-known Attribute`、`Invalid NEXT_HOP`、`Malformed AS_PATH` など）、および **トラブルシューティングのヒント** から原因を特定できます。

BGPShark は NOTIFICATION の data フィールドをデコードして生バイトの上に表示します。

- **エラーコード 3**：問題のパス属性の型とフラグをデコードします（たとえば未知の属性に誤って **Well-known** フラグが付いている場合など）。直前の UPDATE と見比べてください（未対応属性は `UNKNOWN(199) · Transitive · 未デコード` のように表示されます）。
- **その他のエラーコード**：`Bad Peer AS` の不一致 AS 番号、`Unsupported Capability` で拒否されたケイパビリティ、Cease に添付された RFC 9003 のシャットダウンメッセージ（メンテナンス予定やチケット番号が書かれていることがあります）もデコードされます。

### 「特定のプレフィックスが届かない」 {#a-prefix-is-missing}

**経路** 画面で、目的に合わせた照合モードを使って検索します。

- **完全一致** — 指定したプレフィックスそのものを探します。
- **サブネット** — 指定した CIDR より細かい経路が広告されていないか確認します（例：`10.0.0.0/8` で `10.0.12.0/24` を検索）。
- **スーパーネット** — 特定ホスト IP をカバーする集約経路を探します（例：`10.0.12.7`）。

該当する経路が一切見つからない場合、そのセッション上では一度も広告されていないため、対向の広告ポリシーを確認してください。アドレスファミリごと欠落している場合は **セッション** タブの **OPEN の比較** を確認します。

複数の TCP セグメントに分割された UPDATE はパース前に自動再構成されるため、MTU が小さく分割された大規模 UPDATE でも正確なプレフィックス数が集計されます。

### 「ピアが複数経路を持っているのに 1 本しか届かない」 {#only-one-path-arrives-though-the-peer-has-several}

ルートリフレクタやピアは、**ADD-PATH**（RFC 7911）が適切にネゴシエートされない限り、各プレフィックスにつきベストパス 1 本しか広告しません。

セッションを選んで **セッション** タブを開き、ケイパビリティ表の下にある **ADD-PATH ネゴシエーション結果** を確認してください。ADD-PATH は方向性を持つ（送信側が *send*、受信側が *receive* を広告して初めて成立する）ため、双方が *send* のみ設定している場合、上のケイパビリティ表では一致に見えても実際には Path Identifier が送信されません。**ADD-PATH ネゴシエーション結果** では方向・アドレスファミリごとの実際のネゴシエーション結果と不足している設定を確認できます。

ADD-PATH が有効な場合、パケット詳細のプレフィックスには `10.1.0.0/24 path 2` のように Path ID が表示され、経路履歴にも **Path ID** 列が追加されます。これにより「プレフィックス全体が消えた」のか「複数パスのうち 1 本だけが Withdraw された」のかを明確に区別できます。

### 「トラフィックが意図しない上流から出ていく」 {#traffic-leaves-by-the-wrong-upstream}

**経路** で該当プレフィックスを選択すると、ピアごとの広告履歴がベストパス選択に関わる属性（AS_PATH、Next Hop、MED、LOCAL_PREF、Communities）とともに並びます。

![172.20.0.0/16 の経路履歴。短い AS_PATH は MED 300・LOCAL_PREF なし、長い AS_PATH は MED 10・LOCAL_PREF 200 を持つ](manual/s4-bestpath.png)

上の例では、長い AS_PATH の経路が `LOCAL_PREF 200` を持つため優先されます（LOCAL_PREF は AS_PATH 長より先に評価され、短い経路の `MED 300` は比較対象になりません）。

- ハイフン（`-`）はその UPDATE に属性が含まれていなかったことを示し、値 `0` とは区別されます。
- 各属性列は選択した経路にその属性が存在する場合のみ表示され、`ORIGIN` は広告間で値が異なる場合のみ表示されます。

多数のプレフィックスを横断して確認したい場合は、**メッセージ** で `med` や `local_pref` の範囲フィルタが使えます。

```
med > 100
local_pref = 200
prefix = 172.20.0.0/16 and local_pref >= 200
```

MED や LOCAL_PREF を持たない UPDATE はこれらの条件にマッチしません。なお、キャプチャから確認できるのはワイヤ上の広告内容までであり、ルータが実際に RIB へ採用した経路はルータ側で確認してください。

### 「CPU 負荷が高く RIB が収束しない」 {#cpu-is-high-and-the-rib-will-not-settle}

経路チャーンが発生すると、**検出事項** に経路フラップと AS_PATH の変化（それぞれ該当プレフィックスの一覧付き）、Withdraw バーストが表示されます。

![経路フラップと AS_PATH 変化をプレフィックスまで展開し、「Burst of withdrawn prefixes — 60 prefixes withdrawn within 10s」も含む検出事項](manual/s10-churn-alerts.png)

続いて **経路** を開き、**フラップ** 列を 2 回クリックして降順ソートし、最上位のプレフィックスを選択します。

![Flap 数でソートされた Routes 画面。announce と withdraw を交互に繰り返す履歴と、2 つのパスを示す AS_PATH Analysis パネル](manual/s10-churn-routes.png)

**送信元** 列と **AS_PATH 分析** パネルから発生箇所を切り分けられます。

- 1 つのピアから広告と取り消しが規則的に繰り返されている場合、そのピアとのリンクや配下インターフェースが不安定です。
- 同じピアからの広告で複数の AS_PATH が交互に切り替わっている場合、さらに上流のネットワークでフラップが発生しています。

### 「ピアが本来広告すべきでない経路を広告している」 {#a-peer-is-announcing-routes-it-has-no-business-announcing}

経路リークは正常な BGP セッション上で起きるため、**検出事項** には *「問題は検出されませんでした」* と表示されます。

**経路** の検索ボックスに `AS15169` のように AS 番号を入力すると、AS_PATH のどこかにその AS を含む全プレフィックスを絞り込めます。プレフィックスを選択して完全な AS_PATH を確認してください。

![AS15169 を含むプレフィックスで絞り込んだ Routes 画面。8.8.8.0/24 の AS_PATH が AS65100 → AS65001 → AS15169 になっている](manual/s5-route-leak.png)

たとえば顧客 `AS65100` とのセッション上で `AS65100 AS65001 AS15169` が観測される場合、他トランジットから学習した経路が顧客経由で再広告されています。**メッセージ** でも `asn = 15169` で同様に絞り込めます。

### 「ファブリック内のホストが断続的に通信不能になる」 {#a-host-in-the-fabric-drops-out-in-bursts}

EVPN の MAC ムーブは、一方のリーフからの Withdraw と別リーフからの広告の組として現れます。**メッセージ** で対象 MAC アドレスをフィルタしてください。

```
mac = 00:0c:29:aa:bb:cc
```

![特定 MAC で絞り込んだパケット一覧。10.0.0.2 の広告・Withdraw と 10.0.0.1 の広告が並び、Withdraw された経路の RD と VNI がデコードされている](manual/s13-mac-move.png)

`mac`、`vni`、`rd`、`evpn_type` は広告と取り消しの両方にマッチし、詳細ビューで RD・MAC・VNI・ESI がデコードされます。複数の VTEP が短時間に同じ MAC を交互に広告している場合、デュアルホーム設定ミスやブリッジループによる MAC ムーブループが疑われます。

**経路** 画面でも MAC ごとの履歴を追跡でき、**検出事項** ではムーブそのものが *「MAC ムーブ検知」*（移動元と移動先の VTEP を表示）として、*「経路フラップ」* と併せて通知されます。MAC Mobility 拡張コミュニティも詳細ビューでデコードされます（シーケンス番号の自動比較は行いません）。

### 「リロードやソフトクリア後の挙動を確認したい」 {#after-a-reload-or-after-a-soft-clear}

リロードやソフトクリアは大量の BGP パケットを発生させるため、障害と見分けにくくなりがちです。

**Graceful Restart** が行われた場合、**検出事項** には *「セッションフラップを検知しました」* ではなく *「10.0.0.1 が Graceful Restart を実施（ピア: 10.0.0.2）」* と表示されます。この検出事項には要求された **Restart Time**、**転送状態（Forwarding State）の保持有無**、再確立から **End-of-RIB** までの実測収束時間がまとめられます。

![検出事項の warning「10.0.0.1 restarted gracefully, peer 10.0.0.2」。要求された 120s に対し 3.8s で収束し、転送状態を保持したことを表示](manual/s8-graceful-restart.png)

Restart Time 以内に収束し転送状態も保持されていれば warning 表示にとどまりますが、Restart Time を超過した場合や転送状態が保持されなかった場合は **critical** に昇格します。一方、Graceful Restart を使わないクラッシュループは *「セッションフラップを検知しました」* と、切断の検出事項として表示されます。

詳細を確認したい場合は **OPEN の比較** で Graceful Restart の各フラグを確認でき、**メッセージ** では空の UPDATE が `End-of-RIB` とラベル表示されます。

**ソフトクリア（ROUTE-REFRESH）** は ROUTE-REFRESH メッセージと後続の再広告として記録されます。**メッセージ** で ROUTE-REFRESH を選択すると **ROUTE-REFRESH 前後の経路差分** パネルが開き、再広告によって **新規追加**、**再広告されなかった経路**、**属性が変化した経路** の差分が表示されます（変化のない経路は件数のみ表示）。一覧の各経路をクリックすると該当の UPDATE を開けます。

![ROUTE-REFRESH の詳細と「What the refresh changed」パネル。10.0.0.1 が IPv4 Unicast を再広告し、1 経路は変化なし、10.1.1.0/24 がコミュニティ 65001:999 付きで追加されたことを表示](manual/s9-refresh-diff.png)

ソフトクリア後、ピアは現在の経路テーブル全体を再送し、消えた経路について明示的な Withdraw は送りません。そのため、ソフトクリアで失われた経路は Withdraw ではなく **再広告されなかった経路** の一覧で確認します。

キャプチャ範囲に関する次の 2 点は、該当する場合にパネル内へ注記されます。

- セッション途中から取得したキャプチャでは、refresh 前の状態として観測できた経路のみが比較対象になります。
- キャプチャ終了までに End-of-RIB が届いていない場合、未再送の経路も「再広告されなかった経路」として一覧に含まれます。

複数の ROUTE-REFRESH が含まれるキャプチャでは、それぞれのメッセージを選択することで個別の区間を比較できます。

### キャプチャが不完全な可能性を確認する {#the-capture-may-be-lying-to-you}

片方向のパケットしか含まれないキャプチャでは、**検出事項** に *「このセッションは片方向しかキャプチャされていません」* と警告され、セッション一覧ではそのセッションが **重大** と表示されます。ただし、SPAN やキャプチャフィルタの不備と実際の片方向通信障害は BGP 層では見分けがつかないため、まずどちらかを切り分けてください。

**メッセージ** を **すべてのパケット** に切り替え、**送信元** 列と TCP フラグを確認します。

![5 フレームすべてが 10.0.0.1 発で、SYN と ACK はあるが SYN-ACK が欠けているパケット一覧](manual/s12-one-direction.png)

`[S]`（SYN）の次に `[SA]`（SYN-ACK）なしで `[A]`（ACK）が記録されている場合、ホスト自体は対向からの応答を受信しています（そうでなければ ACK を返しません）。したがって、これはネットワーク障害ではなくキャプチャ側で復路を取りこぼしています。

大きなキャプチャでは、**SQL** で送信方向ごとの件数を確認すると素早く判別できます。

```sql
select src_ip, dst_ip, count(*) as frames
from packets group by all order by frames desc
```

双方向が正常に記録されていれば、1 セッションにつき同規模の 2 行が出力されます。1 行のみの場合は片方向の BGP パケットしか含まれていません（`packets` テーブルは BGP パケットのみを格納するため、TCP ハンドシェイクの確認には上の **すべてのパケット** を使用してください）。

## フィルタ {#filters}

フィルタバーは補完付きの 1 行の入力欄です。`/` または `Ctrl+K`（`⌘K`）で入力欄にフォーカスできます。**+ フィルタ** ではメニューから条件を 1 つ組み立てて `and` で追記できます。セッションや期間を選ぶと、フィルタに加えて一覧がさらに絞られます。

パケット詳細でフィルタに使える値には点線の下線が付いています。アドレス・プレフィックス・AS 番号・ネクストホップ・コミュニティにマウスを合わせて **＋** をクリックすると現在のフィルタにその値の条件を追加し、**=** をクリックするとその値だけで絞り込みます。

```
type = NOTIFICATION and src_ip = 10.0.0.1
ip = 10.0.13.1
asn = 65001
prefix = 10.0.0.0/8 and not (type = KEEPALIVE)
capability contains "Route Refresh"
```

複数の条件は `and`、`or`、`not` と括弧で組み合わせられます。演算子は `=`（`==` も可）、`!=`、`contains`、`not contains` に加え、数値フィールドでは `<`、`<=`、`>`、`>=` が利用できます。

フィールド名を付けずに値だけを入力した場合は、最も自然な条件として解釈されます。アドレス（`10.0.13.1`）は `ip = 10.0.13.1`、CIDR（`10.0.0.0/8`）は `prefix = 10.0.0.0/8`、`AS65001` は `asn = 65001`、MAC アドレスは `mac = …`、メッセージ種別（`update`）は `type = UPDATE` になります。

### フィールド一覧 {#fields}

| フィールド | 照合対象 |
|------------|----------|
| `type` | `OPEN`、`UPDATE`、`NOTIFICATION`、`KEEPALIVE`、`ROUTE_REFRESH` |
| `ip` / `peer` | 送信元・宛先のどちらか（`ip = X` は `src_ip = X or dst_ip = X`、`ip != X` は両側とも X でないもの） |
| `src_ip` / `dst_ip` | 送信元 / 宛先 IP アドレス（CIDR 指定で範囲内の全アドレスに一致） |
| `src_port` / `dst_port` | TCP ポート番号（同一 IP ペア間の複数セッションを切り分ける用途） |
| `frame` | フレーム番号（例：`frame >= 100 and frame < 200`） |
| `router_id` | OPEN メッセージの BGP Identifier |
| `src_as` | OPEN メッセージで広告された AS 番号 |
| `asn` | AS_PATH のどこかに含まれる AS 番号 |
| `origin` | `IGP`、`EGP`、`INCOMPLETE` |
| `next_hop` | NEXT_HOP または MP_REACH のネクストホップ |
| `med` | MULTI_EXIT_DISC（範囲比較可。MED を持たない UPDATE には不一致） |
| `local_pref` | LOCAL_PREF（範囲比較可。iBGP のみ。属性がない UPDATE には不一致） |
| `prefix` | 広告または取り消し（Withdraw）されたプレフィックス（経路の履歴全体） |
| `nlri` | 広告されたプレフィックスのみ |
| `withdrawn` | 取り消し（Withdraw）されたプレフィックスのみ |
| `community` | Standard / Large Community |
| `rt` | Route Target（例：`rt = 65001:100`） |
| `ext_community` | 表示形式による Extended Community 全般 |
| `mac` / `vni` / `rd` / `evpn_type` | EVPN 経路の各属性 |
| `capability` | OPEN メッセージのケイパビリティ名 |

以下のエイリアスも利用できます：`src`、`dst`、`as`、`aspath`、`nexthop`、`router-id`、`my_as`、`large-community`、`route-target`、`ext-community`、`evpn-type`。

### プレフィックスと IP アドレスの照合ルール {#how-prefixes-match}

IP アドレスとプレフィックスは文字列ではなく数値としてビット単位で比較されます。たとえば `src_ip = 192.168.0.0/23` は `192.168.0.0` 〜 `192.168.1.255` に正確に一致します。

`prefix` と `withdrawn` では、入力形式によって照合方向が変わります。

- `prefix = 10.0.0.0/8` — 指定 CIDR の **内側** にある経路（`10.0.12.0/24` が一致）
- `prefix = 10.0.12.7` — 指定ホストアドレスを **包含する** 経路
- `prefix contains "10.0.1"` — 部分文字列一致

**経路** 画面の検索も同じロジックで動作します。

### フィルタが効いていないように見えるとき {#when-a-filter-does-not-seem-to-work}

フィルタ式に構文エラーや未知のフィールド名があると、**M 件中 N 件のパケットを表示** カウンタの横に赤いエラーメッセージが表示され、一覧は絞り込まれずに全件表示されたままになります。赤いメッセージが出ている状態で「5 件中 5 件のパケットを表示」と表示されていても、全件一致ではなくフィルタ未適用を意味します。上の表でフィールド名を確認してください。

## BGPShark では判断できないこと {#what-bgpshark-will-not-tell-you}

検出事項が出ていないことをそのまま「問題なし」と誤認しないよう、以下の限界を念頭に置いてください。

- **キャプチャ不備と片方向障害の区別**：片方向しか記録されていないことは検知しますが、キャプチャ側の問題かネットワーク障害かは TCP ハンドシェイクから判断する必要があります（[確認手順](#the-capture-may-be-lying-to-you)）。
- **ルーティングポリシーの妥当性**：期待される AS_PATH や広告ポリシーの情報は持たないため、経路リークは正当な広告と区別されません。
- **ルータ内部の RIB 決定**：キャプチャに記録されるのはワイヤ上を流れたパケットのみです。最終的にどの経路が選択・インストールされたかはルータ上で確認してください。
